# Deployment (Phase 17)

JT-Code starts with Docker Compose; Kubernetes is a later production option, not
a prerequisite for local or initial hosted deployments.

* **Database and auth:** Supabase provides the database, pgvector and authentication.
* **Edge:** Cloudflare sits in front of the cluster.
* **Separate environments:** each environment has its own Supabase project,
  namespace, secrets, Terraform state and GitHub environment.

| Layer | Source | Tooling |
| --- | --- | --- |
| Images | `Dockerfile` (`runtime`, `office`), `streamlit_app/Dockerfile` | Docker Buildx, Trivy, cosign |
| Cluster add-ons, Supabase, namespace and secrets, DNS and WAF | `infra/terraform/{modules,envs}` | Terraform ≥ 1.6 |
| Workloads | `infra/k8s/{base,components,overlays}` | Kustomize, kubectl |
| Pipeline | `.github/workflows/{ci,deploy}.yml`, `scripts/deploy/` | GitHub Actions |
| Local full stack | `docker-compose.yml` (self-hosted Supabase included) | Docker Compose |

## Images

There is one image, and the role is chosen at runtime by `docker/entrypoint.sh`:

* `api`
* `worker` (needs `CELERY_QUEUES`)
* `beat`
* `consumer`
* `migrate`
* `n8n-push`
* `manage …`

The `office` target adds headless LibreOffice for the document worker only.

The images are hardened:

* The base image is pinned by digest.
* Wheels are built in a separate stage; the runtime has no compilers.
* The process runs as UID 10001 under tini, and the code is owned by root.
* Static files are collected at build time.
* The images work with a read-only root filesystem.

CI checks each image:

* hadolint lints the Dockerfiles.
* The tests verify that the user is non-root.
* A Django check runs inside a read-only container.
* Trivy fails the build on fixed HIGH/CRITICAL CVEs and also scans the
  Dockerfiles, manifests and Terraform for misconfiguration.

## Workloads (`infra/k8s`)

`base/` is generated by `scripts/k8s/gen_base.py` (`make k8s-generate`), and CI
fails if it is stale.

| Deployment | Queues / role | Autoscaling |
| --- | --- | --- |
| `jt-code-api` | ASGI API (SSE) | HPA on CPU/memory, PDB `minAvailable` |
| `jt-code-worker-default` | `jobs.default`, `orchestration` | KEDA on Redis queue depth |
| `jt-code-worker-ai` | `jobs.analysis` | KEDA |
| `jt-code-worker-ingestion` | `jobs.ingestion` | KEDA |
| `jt-code-worker-documents` (office image) | `jobs.visualization` | KEDA |
| `jt-code-worker-analytics` | `analytics.analysis`, `analytics.visualization` | KEDA |
| `jt-code-beat` | Celery beat (exactly one, `Recreate`) | none |
| `jt-code-consumer-integrations` | Kafka consumer | none |
| `jt-code-streamlit` | analytics surface | none |
| `jt-code-migrate` (Job) | `migrate` + private bucket verification + `verify_supabase` | run by the deploy script |

Every pod is hardened:

* It runs as non-root, with the RuntimeDefault seccomp profile, a read-only root
  filesystem, all capabilities dropped, and no service-account token.
* It has resource requests and limits.
* `/tmp` and scratch directories are `emptyDir` volumes.
* Namespaces enforce Pod Security `restricted`.

Network policies deny all ingress by default. They then allow the ingress
controller (API and Streamlit) and Prometheus (metrics), and block the cloud
metadata endpoint.

Components (overlays include all three):

* `keda`: ScaledObjects that replace the worker CPU HPAs.
* `monitoring`: ServiceMonitor, PodMonitor, and a PrometheusRule generated from
  `infra/prometheus/alerts.yml`.
* `ingress-hosts`: copies `API_HOST`/`ANALYTICS_HOST` from `config.env` into the Ingress.

Each overlay (`overlays/staging`, `overlays/production`) contains:

* `config.env` for non-secret settings, with each hostname set in one place;
* `streamlit.env`;
* replica and autoscaling bounds;
* image names, which are pinned to digests at deploy time.

## Secrets

`jt-code-secrets` holds exactly the keys in `infra/k8s/secret-keys.txt`.
Terraform (`modules/app_environment`) creates it and refuses to apply if a key
is missing. A test checks that every overlay's `config.env`, plus these keys,
passes the real staging/production settings validation.

* **Generated by Terraform:**
  * `DJANGO_SECRET_KEY`
  * `METRICS_AUTH_TOKEN`
  * `CLOUDFLARE_ORIGIN_SECRET`
  * `N8N_DISPATCH_SECRET`, `N8N_WEBHOOK_SECRET`, `N8N_SENTRY_RELAY_SECRET`
  * `WEBHOOK_SIGNING_SECRET`, `SUPABASE_WEBHOOK_SIGNING_SECRET`
  * the Fernet `TOOL_CREDENTIALS_ENCRYPTION_KEYS`
  * the database password
* **From the Supabase project:** the URLs and service key.
* **External credentials, passed as `TF_VAR_external_secrets`:**
  * Redis (`rediss://`), plus `KEDA_REDIS_ADDRESS` and `KEDA_REDIS_PASSWORD` for KEDA
  * Kafka (SASL_SSL)
  * Supabase Storage (private bucket)
  * Gemini
  * Stripe
  * Sentry DSN
  * `N8N_API_KEY`

The Celery broker must use Redis database **1**, which the KEDA triggers read.

## Reproducible staging from clean infrastructure

Prerequisites:

* An empty Kubernetes cluster and its kube context.
* A Cloudflare zone.
* A Supabase organization.
* Managed Redis (TLS) and Kafka (SASL_SSL).
* An S3-compatible bucket for Terraform state.
* `terraform`, `kubectl` and `kustomize`.

```bash
cd infra/terraform/envs/staging
cp backend.hcl.example backend.hcl            # state location (git-ignored)
cp terraform.tfvars.example staging.tfvars    # non-secret inputs (git-ignored)
export TF_VAR_cloudflare_api_token=… TF_VAR_supabase_access_token=… \
       TF_VAR_grafana_admin_password=… TF_VAR_registry_token=… \
       TF_VAR_external_secrets='{"REDIS_URL":"rediss://…", …}'
cd -
scripts/deploy/bootstrap_environment.sh staging \
  ghcr.io/<owner>/jt-code-api@sha256:… ghcr.io/<owner>/jt-code-api-office@sha256:… \
  ghcr.io/<owner>/jt-code-streamlit@sha256:…
```

The bootstrap runs these steps:

1. **Terraform** creates:
   * the Supabase project and its auth/API settings;
   * the cluster add-ons: ingress-nginx, cert-manager with a Let's Encrypt
     issuer, KEDA, kube-prometheus-stack with the JT-Code dashboards, and the
     OpenTelemetry Collector;
   * the namespace and secrets;
   * Cloudflare DNS for the API, Streamlit and n8n webhooks.
2. **`deploy.sh`** then:
   1. renders the overlay with the given digests;
   2. applies configuration;
   3. runs the **migrate Job**, which must succeed before any workload changes;
   4. applies the workloads and waits for every rollout;
   5. runs an in-cluster health smoke test and **rolls back** if it fails;
   6. deploys and drift-checks the n8n workflows.

Re-running both steps is idempotent. To apply the zone-wide Cloudflare WAF
policy, also apply the production root, which owns the zone policy. Pass it
staging's `origin_secret` output through `other_environment_origin_secrets`.

Deploy n8n itself separately; see `infra/n8n/README.md`.

## Pipeline

* **`ci.yml`** runs on pull requests, on `main`, and weekly as a CVE re-scan:
  * `quality`
  * `test` (Supabase suite, deploy-check, ZAP DAST)
  * `security`
  * `image`
  * `manifests` (generator drift, kustomize render, kubeconform with CRD schemas)
  * `terraform` (fmt, init, validate)
  * `observability-config` (promtool)
  * `workflows` (actionlint)
* **`deploy.yml`** on `main`:
  1. Builds and pushes the three images to GHCR with provenance and SBOM.
  2. Signs them with cosign (keyless, GitHub OIDC) and scans them.
  3. Deploys those **digests** to the `staging` GitHub environment.
* **Production** is a manual `workflow_dispatch` of `deploy.yml` with the
  digests listed in the staging run's summary. It:
  1. verifies the cosign signatures came from this repository's `main` deploy
     workflow;
  2. waits for the `production` environment's required reviewers;
  3. runs the same `deploy.sh`.

GitHub configuration per environment (`staging`, `production`):

* secret `KUBECONFIG`; <!-- pragma: allowlist secret -->
* variables `STAGING_URL` / `PUBLIC_URL`;
* required reviewers on `production`.

## Local full stack

```bash
make compose-up
```

This succeeds without a .env file. To override the documented localhost-only
defaults, copy docker/.env.docker.example to .env and use its
JT_CODE_LOCAL_* variables; do not reuse a managed-Supabase .env for this
self-hosted stack. The launcher prints all browser-facing localhost ports
before startup and opens each ready UI in Chrome or the default browser. Use
make compose-up-no-browser when browser tabs are not wanted.

The default stack runs API/workers, Redis, Redpanda, self-hosted Supabase
(Postgres with pgvector, Auth, PostgREST, private Storage and its local
gateway), n8n backed by its own Postgres, Mailpit, Prometheus, Grafana and
Tempo. All host ports bind to loopback. Sentry has no container: add its DSN
only when an external Sentry project is ready.

The one-shot migrate service waits for Supabase, applies Django migrations and
creates or verifies the private SUPABASE_STORAGE_BUCKET. On a later migration,
run docker compose run --rm migrate. The n8n UI opens on :5678; create an API
key there once and put it in N8N_API_KEY before using workflow deployment.
